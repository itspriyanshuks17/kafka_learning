Topics & Partitions Under Load

Module 2 introduced partitions as the unit of storage. This module is about what happens to that unit under real production conditions: a broker dying mid-write, a partition count decision you can't undo, and how leader election actually resolves.

7.1 How partitioning actually decides where a record goes

The producer's partitioner runs client-side, before the record ever reaches a broker: partition = hash(key) % numPartitions when a key is present, or a sticky round-robin batch strategy when it isn't. This means the producer — not the broker — decides partition placement, and it decides it once, at send time.

7.2 Replication mechanics in detail

Once a record lands on the leader's local log, followers pull it via a fetch request — the same API consumers use, just internal to the cluster. A record is considered committed only once every broker in the ISR has replicated it. Only committed records are visible to consumers (with default isolation settings) — this is what prevents a consumer from reading data that could still disappear if the leader crashes before replication completes.

7.3 Leader election in detail

Clients experience this as a short burst of errors on in-flight requests, followed by automatic recovery once they refresh cluster metadata and discover the new leader — no code changes or manual failover steps needed.

7.4 Choosing a partition count

This decision matters because you can increase partitions later but never decrease them without deleting and recreating the topic. A rough starting formula: partitions = max(desired consumer throughput / per-partition throughput, desired parallel consumers). In practice, most teams start with a number like 6–12 for a moderate-traffic topic and revisit based on real lag metrics (Module 6.5) rather than guessing far ahead.

The irreversible trap — increasing partitions later changes the key-to-partition hash mapping for every existing key, breaking the "same key always lands here" guarantee your consumers may depend on for ordering. Plan generously up front rather than relying on frequent increases.

7.5 Fault tolerance in practice

With replication factor 3 and min.insync.replicas=2, a topic tolerates losing one broker entirely with zero data loss and zero downtime for producers using acks=all — the remaining two ISR members still satisfy the durability requirement. Losing a second broker simultaneously (dropping below min.insync.replicas) causes producers to receive errors rather than silently accepting under-replicated writes.

7.6 Common mistakes

  • Setting min.insync.replicas equal to the full replication factor — this removes all fault tolerance, since losing even one broker blocks all writes.
  • Under-provisioning partition count "to keep it simple," then hitting a consumer-parallelism ceiling months later that requires a disruptive topic recreation.
  • Assuming leader election is instantaneous — it typically takes on the order of seconds; latency-sensitive systems should design for a brief availability gap during broker failure.

7.7 Check your understanding

Q1. Why can a topic's partition count be increased but not decreased?
Partitions are physical, ordered logs on disk. Removing one would mean discarding or somehow merging its ordered history into another partition, which would break both the ordering guarantee and the offset semantics consumers rely on — so Kafka simply disallows it.
Q2. With replication factor 3 and min.insync.replicas=2, how many brokers can fail before acks=all producers start seeing errors?
One. Losing a second broker drops the ISR below min.insync.replicas, and acks=all producers will then receive errors rather than have their writes silently accepted with insufficient durability.

7.8 Summary

Partitioning is decided client-side at send time; replication commits a record only once the full ISR has it; leader election automatically promotes from the ISR and clients recover transparently; and partition count is the one topic setting worth over-planning, since growing it later is easy but shrinking it isn't possible at all.
