AWS MSK (Managed Streaming for Kafka)

MSK runs the actual open-source Kafka broker — nothing proprietary in the wire protocol — but hands broker provisioning, patching, and az-aware replication to AWS. Everything you learned in Modules 2–14 still applies directly; MSK changes the operations layer, not Kafka itself.

17.1 Provisioning a cluster

aws kafka create-cluster \
  --cluster-name production-orders \
  --broker-node-group-info file://broker-nodes.json \
  --kafka-version "3.9.0" \
  --number-of-broker-nodes 3
// broker-nodes.json
{
  "InstanceType": "kafka.m5.large",
  "ClientSubnets": ["subnet-abc", "subnet-def", "subnet-ghi"],
  "StorageInfo": {"EbsStorageInfo": {"VolumeSize": 500}}
}

Spreading brokers across three subnets in three different Availability Zones is what gives you real fault tolerance against an entire AZ outage — this is the cloud-native equivalent of rack awareness.

17.2 IAM authentication

Instead of managing SASL usernames/passwords yourself, MSK supports IAM-based authentication — clients authenticate using the same AWS credentials/roles used everywhere else in your AWS account:

props.put("security.protocol", "SASL_SSL");
props.put("sasl.mechanism", "AWS_MSK_IAM");
props.put("sasl.jaas.config",
    "software.amazon.msk.auth.iam.IAMLoginModule required;");
props.put("sasl.client.callback.handler.class",
    "software.amazon.msk.auth.iam.IAMClientCallbackHandler");

Authorization then flows through standard IAM policies attached to the calling role, rather than Kafka ACLs (Module 12.3) managed separately — one less system to keep in sync with your access model.

17.3 Monitoring & scaling

  • CloudWatch integration — broker and topic metrics (the same shortlist from Module 13.2) flow into CloudWatch automatically, no self-hosted exporter needed.
  • Storage auto-scaling — MSK can automatically increase EBS volume size as usage approaches a configured threshold, avoiding the "brokers stopped accepting writes because disk filled up" failure mode from Module 13.5.
  • Broker scaling — adding brokers is an API call, but existing partitions don't automatically rebalance onto new brokers; a partition reassignment still has to be triggered.

17.4 MSK Serverless

A variant that removes broker/capacity planning entirely — you interact only with topics and pay per throughput, at the cost of some configuration flexibility (fewer broker-level settings exposed) compared to provisioned MSK.

17.5 Common mistakes

  • Provisioning all brokers in a single AZ/subnet — defeats the fault-tolerance purpose of a multi-broker cluster entirely.
  • Assuming storage auto-scaling replaces monitoring — it buys time, but sustained under-provisioning still needs a real capacity review.
  • Mixing IAM auth expectations with client libraries that don't support the AWS_MSK_IAM SASL mechanism out of the box — requires the separate aws-msk-iam-auth library shown above.

17.6 Summary

MSK runs unmodified open-source Kafka, so everything from Modules 2–14 transfers directly — what changes is that AWS handles broker provisioning, patching, and (optionally) IAM-based auth and storage auto-scaling. Multi-AZ subnet placement is the one MSK-specific decision that most directly determines your real fault tolerance.
