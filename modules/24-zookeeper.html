ZooKeeper — coordination for distributed systems

ZooKeeper provides a simple, reliable coordination service used by Apache Kafka (pre-KRaft) for metadata, leader election, and cluster membership. This page answers: what ZooKeeper is, why Kafka used it, how it works, when it's required, and where it fits in an architecture. Includes diagrams and operational notes.

What What is ZooKeeper?

ZooKeeper is a distributed coordination service exposing a hierarchical namespace (similar to a filesystem) of znodes. It offers primitives for configuration, naming, leader election, and distributed synchronization. ZooKeeper guarantees sequential consistency, atomicity, and single-system image semantics.

Why Why Kafka used ZooKeeper

  • Store broker metadata (which brokers exist, what topics/partitions live where).
  • Election of partition leaders: ZooKeeper helps elect controller and partition leaders.
  • Store controller state and configuration in a highly-available, small-data store.
  • Simplifies distributed coordination primitives—Kafka relied on that to avoid custom implementations.

How How ZooKeeper works (high level)

ZooKeeper runs as an ensemble of odd-numbered nodes (3,5,7). Clients connect to any node. Writes go through the leader and are replicated to followers using Zab (ZooKeeper Atomic Broadcast). Reads can be served by any node (often from leader to guarantee monotonic reads).

Where Where ZooKeeper runs

ZooKeeper should run on dedicated nodes (not co-located with heavy I/O brokers) with low-latency networking. Use an odd number of nodes (3,5) and colocate with low-latency zones. Avoid running on the same host as Kafka brokers in production to reduce coupling and blast radius.

When When is ZooKeeper required

Historically, Kafka (pre-KRaft) required ZooKeeper for metadata and leader election. Newer Kafka (KRaft mode) removes the dependency by embedding the controller inside Kafka itself. Use ZooKeeper if: running older Kafka versions or migrating from existing ZooKeeper-based clusters.

Operational workflows Common operational workflows

Leader election (controller)

When a controller fails, ZooKeeper coordinates a new controller election. Steps:

  1. ZooKeeper detects the controller ephemeral znode lost (session expired).
  2. Remaining brokers attempt to create the controller znode; the successful one becomes controller.
  3. New controller reads metadata from ZooKeeper and starts managing partition leader assignments.

Metadata storage and watches

ZooKeeper stores small metadata (topic/partition assignments, config). Kafka brokers set watches on znodes and react to changes. Watches are one-time triggers — code must re-establish watches after events.

Best practices

  • Run ZooKeeper on 3 or 5 dedicated nodes with stable networking.
  • Keep ZooKeeper data small and tuned (snapshot + txn logs); avoid storing large blobs.
  • Monitor session expirations, Zxid growth, and leader election rate.
  • Plan maintenance windows; rolling restarts should be done one node at a time to preserve quorum.
  • For new deployments, prefer Kafka's KRaft mode to avoid ZooKeeper dependency where possible.
