Troubleshooting

A field guide organized by symptom. Each one names the metric or command that confirms the diagnosis before you touch anything.

22.1 Symptom: rising consumer lag

bin/kafka-consumer-groups.sh --describe --group my-group --bootstrap-server localhost:9092
  • Check consumer count vs partition count — if consumers = partitions already, you're at the parallelism ceiling (Module 2.11); adding more partitions (and consumers) is the only real fix.
  • Check per-record processing time — a slow downstream call (DB write, external API) inside the poll loop is the most common root cause, not CPU or network.
  • Check for frequent rebalances — each one pauses the whole group briefly; look for consumers dropping in/out due to max.poll.interval.ms being exceeded.

22.2 Symptom: constant/frequent rebalancing

  • Increase max.poll.interval.ms if processing legitimately takes longer than the default, or reduce max.poll.records so batches finish faster.
  • Check for consumer instances crashing and restarting in a loop — the rebalance is a symptom, the crash is the disease.
  • Switch to CooperativeStickyAssignor (Module 6.4) if you're still on the default eager assignor — it shrinks the pause even when rebalances do happen.

22.3 Symptom: broker out of disk

This is the failure mode that doesn't degrade gracefully — writes simply stop. Immediate mitigation: reduce retention.ms/retention.bytes on the largest topics to force faster segment deletion, or add disk capacity if infrastructure allows it live. Longer-term: alert on disk usage trend well before this point (Module 13.5), not just at the crisis threshold.

22.4 Symptom: broker failure / unplanned restart

bin/kafka-topics.sh --describe --under-replicated-partitions --bootstrap-server localhost:9092
  • Check UnderReplicatedPartitions — nonzero means some partitions temporarily have fewer in-sync replicas than expected while the broker recovers.
  • Confirm leader election happened cleanly (Module 7.3) — clients should recover automatically once they refresh metadata; persistent errors past a few seconds suggest a deeper networking or config issue.
  • Once the broker rejoins, its replicas need time to catch back up — watch ISR membership return to full before considering the incident closed.

22.5 Symptom: leader election problems / no active controller

bin/kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status

ActiveControllerCount should be exactly 1 cluster-wide. Zero or more than one indicates a controller quorum problem — check network connectivity between controller nodes and quorum voter configuration (controller.quorum.voters) for mismatches.

22.6 Symptom: producer errors under load

  • NotEnoughReplicasException — ISR has dropped below min.insync.replicas; check for broker issues first (Module 22.4).
  • TimeoutException on send — often a buffer.memory too small for the burst rate, or a genuinely overloaded broker (check request latency percentiles, Module 13.2).
  • RecordTooLargeException — message exceeds max.request.size/broker's message.max.bytes; either raise the limit deliberately or reconsider whether Kafka is the right transport for that payload size.

22.7 Symptom: schema registration rejected

This is usually the registry working correctly, not a bug (Module 11.4) — a field removal or type change violates the configured compatibility mode. Confirm the intended compatibility mode first; if the change is genuinely necessary, it needs a coordinated multi-step rollout (deprecate, transition, remove), not a compatibility-mode override.

22.8 Diagnostic checklist, in order

  1. Confirm which layer the symptom is in: producer, broker/cluster, or consumer.
  2. Pull the relevant metric or CLI command from this module before changing any config.
  3. Check recent changes first — partition count changes, schema deploys, and consumer deploys explain most incidents more often than "Kafka itself broke."
  4. Fix the root cause, then verify the specific metric (lag, ISR, controller count) returns to a healthy baseline — not just that the alert stopped firing.

22.9 Summary

Nearly every Kafka incident maps to one of a handful of root causes covered across this handbook — parallelism ceilings, ISR/durability settings, disk exhaustion, or a schema/config change. The kafka-consumer-groups.sh --describe and JMX metrics from Module 13 are almost always the first two things worth checking, before anything else.
