Introduction to Apache Kafka

Before touching a single config file, you need to know what problem Kafka actually exists to solve — and it isn't "sending messages." It's making an entire company's worth of systems agree on what happened, and in what order.

1.1 What is Apache Kafka?

Apache Kafka is a distributed event streaming platform. That phrase gets thrown around loosely, so break it into its three real claims:

  • Distributed — it runs as a cluster of machines (brokers), not one server. Data is split and copied across them, so no single machine failing takes the system down.
  • Event streaming — instead of storing the current state of something (like a database row), Kafka stores the sequence of things that happened — "order placed," "payment confirmed," "item shipped" — each as an immutable event, forever ordered the way they occurred.
  • Platform — it isn't just a message broker. It bundles publish/subscribe messaging, durable storage, and stream processing (Kafka Streams) into one system.

The cleanest mental model: Kafka is a distributed, append-only commit log that many programs can write to and read from independently, at their own pace, without ever blocking each other.

Analogy — think of Kafka like a bank's transaction ledger, not a bank's account balance display. The ledger never edits a past entry; it only appends new ones. Anyone can replay the ledger from any point to reconstruct any balance at any time. That's exactly how a Kafka topic behaves.

1.2 Why Kafka? The problem before Kafka

Picture a mid-size e-commerce company with these systems: Order Service, Inventory Service, Payment Service, Email Service, Analytics Warehouse, and Fraud Detection. Without a streaming platform, every time an order is placed, Order Service has to directly call all five other systems.

This "point-to-point" mesh has three concrete failures baked in:

  • Tight coupling — Order Service needs to know about, call, and handle failures for every downstream system. Adding a new consumer (say, a loyalty-points service) means changing Order Service's code.
  • Cascading failure — if Email Service is slow, does Order Service wait? If it calls synchronously, a slow or down consumer can stall the entire order flow.
  • No replay — if Analytics Warehouse was down for an hour, or a new service joins the company today and needs the last six months of orders, that data is just gone unless someone built a separate backfill pipeline.

Kafka's fix: Order Service publishes one event — OrderPlaced — to a Kafka topic. It doesn't know or care who's listening. Every other service subscribes independently, reads at its own pace, and can even be added a year later and replay history from day one.

1.4 Problems Kafka solves

  • Decoupling producers from consumers — services publish without knowing who (if anyone) is listening.
  • Absorbing traffic spikes — Kafka acts as a buffer; a burst of 10x normal traffic gets written to the log and consumers drain it at their own sustainable pace instead of falling over.
  • Replayability — because events are retained (not deleted after delivery like a traditional queue), you can reprocess historical data — fix a bug in a consumer, then replay the last 7 days to correct the output.
  • Ordering guarantees — within a partition, events are strictly ordered. "Payment confirmed" can never be processed before "Order placed" for the same order key.
  • Multi-consumer fan-out without duplication of effort — ten different teams can each read the same stream independently, without the producer doing anything differently.
  • Integrating a heterogeneous company — Java, Python, Go, and legacy systems can all speak Kafka's wire protocol, so it becomes the shared nervous system of the company's data.

1.5 Kafka vs RabbitMQ vs Redis

This is one of the most common interview questions in Module 20, so get the distinctions precise now:

ThroughputVery high (millions of msgs/sec, built for it)High, but lower than Kafka at extreme scaleVery high, but bounded by RAM and single-node durability tradeoffs

One-line answer for interviews — RabbitMQ is a smart broker with dumb consumers (it tracks who read what); Kafka is a dumb broker with smart consumers (each consumer tracks its own offset). That single design choice explains most of the differences above.

1.6 Real-world use cases

  • Log aggregation — collecting logs from thousands of services into one durable stream for centralized processing (this was Kafka's original use case at LinkedIn).
  • Activity tracking — page views, clicks, and searches streamed in real time to power recommendations.
  • Metrics & monitoring — operational metrics from distributed systems, fed into Prometheus/Grafana pipelines (Module 13).
  • Event sourcing — using the log itself as the system of record instead of a database (Module 19).
  • CDC (Change Data Capture) — streaming row-level database changes into Kafka via Kafka Connect (Module 9) to keep downstream systems in sync.
  • Fraud detection — scoring transactions in real time as they stream through, rather than in a nightly batch job.
  • Financial trading platforms, ride-sharing dispatch, IoT sensor ingestion — anywhere "a huge number of small events, in order, at low latency" describes the workload.

1.7 Event-driven architecture

In an event-driven architecture, services communicate by producing and reacting to events — facts about something that already happened — rather than by calling each other's APIs and waiting for a response. Three properties define it:

  • Asynchronous — the producer doesn't block waiting for consumers to finish.
  • Immutable — an event like OrderPlaced is a historical fact; it's never updated, only new events are appended (e.g. OrderCancelled).
  • Fact-based, not command-based — an event says "this happened," not "please do this." What each consumer does in response is entirely up to it.

1.8 Pub/Sub model vs Queue model

Kafka is usually described as "publish/subscribe," but it actually lets you implement both classic messaging models on the same topic, just by how you configure consumer groups (full detail in Module 6):

Put multiple consumers in the same consumer group and Kafka behaves like a traditional queue: the group divides up partitions so each message is processed once, by one consumer, enabling parallel throughput. Put consumers in different consumer groups and each group independently receives every message — classic pub/sub fan-out. You get both models, for free, from the same storage layer.

1.9 The Kafka ecosystem

  • Kafka Core — the brokers, storage, and replication protocol covered in Module 2.
  • Kafka Connect — pluggable, config-driven connectors to move data in/out of Kafka without hand-writing producer/consumer code (Module 9).
  • Kafka Streams — a Java library for building stream-processing applications directly on top of Kafka (Module 10).
  • Schema Registry — enforces and versions the shape of your data (Avro/Protobuf/JSON) so producers and consumers don't silently break each other (Module 11).
  • ksqlDB — SQL-like queries over streaming data, built by Confluent.
  • KRaft — Kafka's built-in consensus layer that replaced the ZooKeeper dependency.

1.10 Common beginner mistakes

  • Thinking of Kafka as "just a faster queue" — it's a log; messages aren't removed after being read, which changes how you design consumers entirely.
  • Assuming global ordering across a whole topic — ordering is only guaranteed within a single partition (Module 7).
  • Treating Kafka as a database for point lookups — it's built for sequential, ordered access, not random-access queries.
  • Forgetting that consumers, not the broker, track their own read position (the offset) — this is core to why Kafka scales the way it does.

1.11 Check your understanding

Q1. Why is Kafka described as a "commit log" rather than a "message queue"?
Because messages aren't deleted once consumed — they're retained (based on a retention policy) and can be replayed by any consumer from any offset. A traditional queue removes a message once it's acknowledged.
Q2. Two teams need to process the same order events completely independently. How does Kafka support this without either team affecting the other?
Put each team's consumers in a separate consumer group. Kafka delivers a full copy of the topic's data to every consumer group independently — this is the pub/sub behavior described in 1.8.
Q3. What's the one-sentence difference between RabbitMQ and Kafka that explains most of their other differences?
RabbitMQ is a smart broker with dumb consumers (the broker tracks delivery state); Kafka is a dumb broker with smart consumers (each consumer tracks its own offset).

1.12 Summary

Kafka is a distributed, append-only log that decouples producers from consumers, retains data instead of deleting it on read, guarantees strict ordering within a partition, and can behave as either a queue or a pub/sub system depending purely on consumer group configuration. That one storage primitive — the log — is what every other module in this handbook builds on.
