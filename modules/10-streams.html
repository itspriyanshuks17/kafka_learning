Kafka Streams

Kafka Streams is a Java library — not a separate cluster to run — for building stream-processing applications directly on top of topics. The core idea to internalize: a stream and a table are two views of the same data, and Streams lets you move fluidly between them.

10.1 KStream vs KTable — the stream-table duality

KStreamKTable
RepresentsAn unbounded sequence of independent eventsThe latest value per key — a continuously updated table
Underlying storageRegular topicCompacted topic (Module 8.3) + local state store
AnalogyBank transactionsCurrent account balance
New record with same keyBoth records kept, in orderNew record replaces the old value for that key

10.2 A basic topology

StreamsBuilder builder = new StreamsBuilder();

KStream<String, String> orders = builder.stream("orders");

KStream<String, String> highValue = orders
    .filter((key, value) -> extractAmount(value) > 1000)
    .mapValues(value -> enrich(value));

highValue.to("high-value-orders");

KafkaStreams streams = new KafkaStreams(builder.build(), props);
streams.start();

10.3 Aggregations

KTable<String, Long> orderCountByCustomer = orders
    .groupBy((key, value) -> extractCustomerId(value))
    .count();

orderCountByCustomer.toStream().to("orders-per-customer");

Every aggregation like count(), reduce(), or aggregate() produces a KTable, backed by a local state store (RocksDB by default) and a compacted changelog topic that lets state be rebuilt if an instance restarts or moves to another machine.

10.4 Windowing

Aggregating "forever" often isn't useful — you want counts per 5-minute window. Windowing buckets events by time before aggregating:

KTable<Windowed<String>, Long> ordersPer5Min = orders
    .groupBy((key, value) -> extractCustomerId(value))
    .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5)))
    .count();
Window typeBehavior
TumblingFixed-size, non-overlapping windows (e.g. every 5 min, cleanly)
HoppingFixed-size, overlapping windows (e.g. 5-min window every 1 min)
SlidingA window per pair of events within a time bound of each other
SessionDynamic-size windows that close after a period of inactivity — natural fit for user session analytics

10.5 Joins

Joins combine two streams/tables by key — the same relational concept, adapted for unbounded data:

  • KStream–KStream join — joins two event streams within a time window (e.g. matching a click with a later purchase within 10 minutes).
  • KStream–KTable join — enriches a stream of events with the latest value from a table (e.g. enrich an order event with the customer's current tier from a customers KTable).
  • KTable–KTable join — joins two tables, producing a new continuously-updated table.
KStream<String, String> enrichedOrders = orders.join(
    customersTable,
    (order, customer) -> combine(order, customer)
);

10.6 Exactly-once processing

Setting processing.guarantee=exactly_once_v2 wraps the read-process-write cycle in a Kafka transaction (Module 5.8) — consuming input, updating state, and producing output all commit or roll back together, so a crash mid-processing never produces duplicate or partial output.

10.7 Common mistakes

  • Confusing a KTable's "latest value wins" semantics with a KStream's "every event kept" semantics when choosing the wrong abstraction for the job.
  • Ignoring state store sizing — RocksDB state for large keyspaces needs real disk and memory planning, not just default settings.
  • Using tumbling windows for user-session-style analysis where session windows are the natural fit — tumbling windows will split one real session across multiple fixed buckets.

10.8 Check your understanding

Q1. Two records arrive with the same key — one on a KStream, one on a KTable. What's different about how each is handled?
On a KStream both records are kept and processed independently, in order. On a KTable the second record replaces the first as the current value for that key — only the latest value per key is retained.
Q2. Why is a session window a better fit than a tumbling window for analyzing user browsing sessions?
A tumbling window has a fixed boundary that can arbitrarily split one continuous user session across two buckets. A session window's size is determined by actual inactivity gaps, so it naturally captures a full session regardless of how long it lasted.

10.9 Summary

Kafka Streams treats streams and tables as two sides of the same coin — every aggregation turns a stream into a table, backed by a compacted changelog topic. Windowing bounds "forever" aggregations into meaningful time buckets, joins combine streams and tables by key, and exactly-once processing extends Kafka's transactional guarantees across the whole read-process-write cycle.
