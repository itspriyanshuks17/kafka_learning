Kubernetes (Strimzi)

Kafka has strong opinions about identity (broker IDs), storage (persistent, per-broker disks), and startup order — exactly the things vanilla Kubernetes Deployments handle badly. Strimzi packages Kafka's needs into a Kubernetes-native operator so you describe desired state and it manages the rest.

16.1 Why not just write raw manifests?

A hand-written Deployment treats pods as interchangeable — exactly wrong for Kafka brokers, which need stable identity and stable storage across restarts. Strimzi uses StatefulSets under the hood (stable network identity, ordered startup, one PVC per broker) and layers Kafka-specific lifecycle logic — rolling upgrades, certificate rotation, rack-aware replica placement — on top.

16.2 Installing Strimzi via Helm

helm repo add strimzi https://strimzi.io/charts/
helm install kafka-operator strimzi/strimzi-kafka-operator \
  --namespace kafka --create-namespace

16.3 Defining a Kafka cluster as a Custom Resource

apiVersion: kafka.strimzi.io/v1beta2
kind: Kafka
metadata:
  name: my-cluster
  namespace: kafka
spec:
  kafka:
    version: 3.9.0
    replicas: 3
    listeners:
      - name: plain
        port: 9092
        type: internal
        tls: false
    storage:
      type: persistent-claim
      size: 100Gi
    config:
      offsets.topic.replication.factor: 3
      default.replication.factor: 3
      min.insync.replicas: 2
  entityOperator:
    topicOperator: {}
    userOperator: {}
kubectl apply -f my-cluster.yaml -n kafka
kubectl get pods -n kafka
# my-cluster-kafka-0, my-cluster-kafka-1, my-cluster-kafka-2 — one per broker, stable names

16.4 Managing topics declaratively

With the Topic Operator enabled above, topics become Kubernetes Custom Resources too — creating a topic is a kubectl apply, not a manual CLI call, which fits naturally into GitOps workflows:

apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaTopic
metadata:
  name: orders
  labels:
    strimzi.io/cluster: my-cluster
spec:
  partitions: 6
  replicas: 3

16.5 StatefulSets under the hood

Each broker pod gets a predictable DNS name (my-cluster-kafka-0.my-cluster-kafka-brokers), its own PersistentVolumeClaim that survives pod rescheduling, and ordered, one-at-a-time rolling restarts — critical since restarting all brokers simultaneously would take the whole cluster's leadership down at once.

16.6 Common mistakes

  • Writing raw Deployments/StatefulSets by hand instead of using an operator — reinventing rolling-restart-with-leader-awareness logic that Strimzi already solved.
  • Undersizing persistent volume storage class performance — Kafka's disk-throughput sensitivity (Module 8.5) applies just as much inside Kubernetes.
  • Not setting pod anti-affinity / rack awareness — letting all three broker pods land on the same physical node defeats the purpose of replication factor 3.

16.7 Summary

Strimzi turns Kafka's operational complexity — stable identity, ordered restarts, persistent per-broker storage — into a declarative Custom Resource, backed by StatefulSets. Combined with the Topic Operator, an entire Kafka cluster and its topics can live in Git and be managed the same way as the rest of a Kubernetes-native stack.
