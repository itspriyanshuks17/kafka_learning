Kafka Connect

Most data doesn't originate as a hand-written producer call — it lives in a Postgres table or needs to end up in Elasticsearch. Connect exists so you configure that movement in JSON instead of writing and operating custom producer/consumer code for every integration.

9.1 Source vs Sink connectors

  • Source connector — pulls data into Kafka from an external system (a database, an API, a file directory).
  • Sink connector — pushes data out of Kafka into an external system (a search index, a data warehouse, object storage).

9.2 Connect worker modes

  • Standalone — single process, config in a local file; fine for local development, not for production.
  • Distributed — a cluster of worker processes coordinating via Kafka itself, submitting connector configs via a REST API; this is what you run in production, since it gives you fault tolerance and horizontal scaling for connector tasks.

9.3 JDBC source connector (CDC-style)

{
  "name": "jdbc-orders-source",
  "config": {
    "connector.class": "io.confluent.connect.jdbc.JdbcSourceConnector",
    "connection.url": "jdbc:postgresql://db:5432/shop",
    "table.whitelist": "orders",
    "mode": "incrementing",
    "incrementing.column.name": "id",
    "topic.prefix": "db-"
  }
}

Submitted to the REST API: POST /connectors with the JSON body above. Connect polls the table on an interval and produces a record per new/changed row to db-orders.

9.4 Elasticsearch sink connector

{
  "name": "es-orders-sink",
  "config": {
    "connector.class": "io.confluent.connect.elasticsearch.ElasticsearchSinkConnector",
    "connection.url": "http://elasticsearch:9200",
    "topics": "db-orders",
    "key.ignore": "true",
    "type.name": "_doc"
  }
}

9.5 S3 sink connector

{
  "name": "s3-orders-sink",
  "config": {
    "connector.class": "io.confluent.connect.s3.S3SinkConnector",
    "s3.bucket.name": "analytics-lake",
    "topics": "db-orders",
    "format.class": "io.confluent.connect.s3.format.parquet.ParquetFormat",
    "flush.size": "1000"
  }
}

9.6 Common mistakes

  • Running standalone mode in production — no fault tolerance if the single worker process dies.
  • JDBC source in incrementing mode against a table with updates (not just inserts) — it will miss updates to existing rows; use timestamp+incrementing mode or proper log-based CDC (e.g. Debezium) for update-heavy tables.
  • Forgetting Schema Registry integration (Module 11) when connectors on both ends expect structured data — mismatched or missing schemas break sink connectors downstream.

9.7 Summary

Kafka Connect turns data integration into configuration instead of code: source connectors bring external data in, sink connectors push Kafka data out, and distributed mode gives you the fault tolerance to run this reliably in production — all managed through a REST API rather than custom producer/consumer applications.
