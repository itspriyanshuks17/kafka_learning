Monitoring

Kafka exposes an enormous amount of internal state via JMX. The skill isn't knowing every metric — it's knowing the handful that actually predict an incident before it happens.

13.1 JMX — where every metric comes from

Kafka is a JVM application, so every broker, producer, and consumer metric is exposed as a JMX MBean. Enable remote JMX on a broker:

export JMX_PORT=9999
export KAFKA_JMX_OPTS="-Dcom.sun.management.jmxremote.authenticate=false \
  -Dcom.sun.management.jmxremote.ssl=false"
bin/kafka-server-start.sh config/server.properties

13.2 The metrics that actually matter

MetricWhy it matters
UnderReplicatedPartitionsNon-zero means some partition has fewer in-sync replicas than expected — an early durability warning
ActiveControllerCountShould be exactly 1 cluster-wide; 0 or >1 signals a controller election problem
Consumer group lagThe clearest signal a consumer can't keep up (Module 6.5)
RequestQueueSize / request latency percentilesRising p99 latency on produce/fetch requests is an early sign of broker overload
BytesInPerSec / BytesOutPerSecRaw throughput per broker — useful for spotting hot brokers or hot partitions
Disk usage per brokerKafka doesn't degrade gracefully when it runs out of disk — this needs hard alerting, not just dashboards

13.3 Kafka Exporter + Prometheus

kafka_exporter (or the JMX Exporter Java agent) scrapes broker JMX metrics and exposes them in Prometheus format:

docker run -d --name kafka-exporter -p 9308:9308 \
  danielqsj/kafka-exporter --kafka.server=kafka:9092
# prometheus.yml
scrape_configs:
  - job_name: 'kafka'
    static_configs:
      - targets: ['kafka-exporter:9308']

13.4 Grafana dashboards

Once Prometheus is scraping, a Grafana dashboard built on the exported metrics typically tracks, per topic and per consumer group: lag over time, bytes in/out per second, under-replicated partition count, and request latency percentiles — the same shortlist from 13.2, visualized.

13.5 Common mistakes

  • Dashboarding everything JMX exposes with no alerting on the handful of metrics that actually predict failure.
  • Alerting on absolute lag numbers instead of lag trend — a stable lag of 50,000 on a high-throughput topic can be healthy; a rapidly growing lag of 500 is the real warning sign.
  • No disk-usage alerting — Kafka brokers that run out of disk stop accepting writes entirely, and by the time it shows up as a customer-facing incident it's too late for a graceful fix.

13.6 Summary

JMX is the source of truth for every Kafka metric; kafka_exporter/JMX Exporter bridges that into Prometheus; Grafana visualizes it. The real skill is alerting on the small set of metrics — under-replicated partitions, controller count, lag trend, and disk usage — that actually predict incidents rather than drowning in dashboards.
