Kafka in Microservices

Four patterns come up in almost every serious microservices system built around Kafka. Each solves a specific failure mode that shows up once you stop using a single database transaction to hold everything together.

19.1 The Saga pattern

A single business transaction (placing an order) now spans multiple services (inventory, payment, shipping) with no shared database transaction. A saga coordinates this as a sequence of local transactions, each publishing an event that triggers the next step — and if any step fails, publishing compensating events that undo the prior steps.

The choreography style shown above lets each service react to events independently; an orchestration style instead has a central saga coordinator explicitly telling each service what to do next — a trade-off between decentralization and traceability.

19.2 CQRS (Command Query Responsibility Segregation)

Separates the model used to write data (commands) from the model used to read it (queries). Kafka is the natural glue: a write updates the source-of-truth service and publishes an event; a Kafka Streams job or Connect sink (Modules 9–10) projects that event into one or more read-optimized views — a search index, a denormalized cache, a reporting table — each shaped for its specific query pattern.

19.3 Event Sourcing

Instead of storing current state directly, the system stores the full sequence of events that produced it — the log itself is the system of record. Current state is derived by replaying events (exactly the compaction/KTable mechanism from Modules 8.3 and 10.1). This gives you a complete audit trail for free and the ability to rebuild any projection from scratch just by replaying history.

19.4 The Outbox pattern

A classic bug: a service updates its own database and separately publishes a Kafka event — but a crash between the two steps leaves the database updated with no event ever published (or vice versa). The outbox pattern fixes this by writing the event into an "outbox" table in the same local database transaction as the business update, then using Kafka Connect's Debezium CDC source connector (Module 9.3) to stream that outbox table into Kafka — guaranteeing the event is published if and only if the business transaction committed.

Why this matters — the outbox pattern is what actually closes the "dual write" gap that a naive "update DB, then call producer.send()" approach leaves open, without needing distributed transactions across the database and Kafka.

19.5 Common mistakes

  • Implementing a saga without compensating actions for every step that can fail — a partial failure then leaves the system in a permanently inconsistent state.
  • Choosing orchestration for its clearer traceability, then building a single point of failure into the orchestrator without realizing it.
  • Skipping the outbox pattern and hitting the classic dual-write bug under real production failure conditions (the crash always happens at the worst possible moment).

19.6 Check your understanding

Q1. What specific bug does the outbox pattern prevent that a plain "write to DB, then call producer.send()" doesn't?
A crash between the database write and the Kafka send leaves the two systems inconsistent — the DB update happened but the event never published, or vice versa. Writing the event to an outbox table in the same DB transaction, then streaming that table via CDC, guarantees the event is published exactly when the business transaction commits.

19.7 Summary

Sagas coordinate multi-service transactions through events plus compensating actions; CQRS uses Kafka to project one source of truth into many read-optimized views; event sourcing makes the log itself the system of record; and the outbox pattern closes the dual-write gap between a local database and Kafka. All four patterns lean on properties already covered — ordering, compaction, and replay — introduced in earlier modules.
