Hands-on Projects

Eight builds, ordered roughly by difficulty. Each one is deliberately designed to force you to use a specific module's concepts for real, rather than just reading about them.

21.1 Project 1 — Real-time chat application

Concepts exercised: topics per chat room, keying by room ID for ordering (Module 5.4), consumer groups per connected client.

One topic per room (or one topic with room ID as key), a WebSocket gateway service that produces messages and consumes them back out to connected clients. The interesting problem: each connected browser needs its own view of the stream, which means each WebSocket connection needs its own consumer group — not shared — since every connected client should see every message, not compete for messages like a work queue.

21.2 Project 2 — Food delivery order tracking

Concepts exercised: event sourcing (Module 19.3), KTable for "current order status" (Module 10.1).

Every state change (OrderPlaced, DriverAssigned, PickedUp, Delivered) is an event on an order-events topic, keyed by order ID. A Kafka Streams job folds this into a KTable of current status per order, which a small API serves to the tracking UI — this is CQRS (Module 19.2) in miniature.

21.3 Project 3 — Stock market stream processor

Concepts exercised: windowing (Module 10.4), high-throughput producer tuning (Module 14.1).

A producer simulates or ingests a real tick stream keyed by ticker symbol. A Kafka Streams topology computes rolling VWAP (volume-weighted average price) using tumbling or hopping windows, publishing results to a downstream topic that a dashboard consumes.

21.4 Project 4 — Ride-hailing dispatch

Concepts exercised: KStream-KTable join (Module 10.5), saga pattern (Module 19.1).

A stream of ride requests joined against a KTable of currently available drivers (updated by driver-location-ping events) to find matches. Once matched, a small saga coordinates DriverAssigned → RideAccepted/RideRejected → re-match on rejection.

21.5 Project 5 — Order management with the Outbox pattern

Concepts exercised: outbox pattern (Module 19.4), Kafka Connect + Debezium (Module 9.3).

A Spring Boot order service (Module 18) writes both the order row and an outbox event row in one local database transaction. A Debezium CDC source connector streams the outbox table into Kafka — deliberately built to expose the dual-write bug first (by skipping the outbox table), then fix it, so you feel the failure mode directly.

21.6 Project 6 — Centralized log aggregation

Concepts exercised: Kafka's original use case, retention tuning (Module 8.2), monitoring (Module 13).

Multiple services ship logs to a shared app-logs topic; a sink connector (Module 9.4) pushes them into Elasticsearch for search, while a separate long-retention topic keeps raw logs for compliance. Good project for practicing dashboarding lag and throughput (Module 13.4).

21.7 Project 7 — IoT sensor monitoring

Concepts exercised: partition key design for many independent devices (Module 5.4), session windows (Module 10.4).

Thousands of simulated sensors publish readings keyed by device ID. A Streams job flags anomalies (value outside a rolling bound) and uses session windows to detect "device went offline" (a session that never closes with a new reading).

21.8 Project 8 — Real-time fraud detection pipeline

Concepts exercised: everything — exactly-once processing (Module 5.8/10.6), multi-topic joins, schema evolution (Module 11), security (Module 12).

Transaction events joined against a KTable of recent transaction history per account (velocity checks — "5 transactions in 60 seconds"), scored, and high-risk transactions routed to a review topic with SASL_SSL + ACLs enforced end to end. This is the capstone project — it's intentionally the one that requires nearly every module in this handbook.

21.9 Summary

Start with Project 1 or 2 if you're still solidifying Modules 5–8; jump to Project 5 once Module 19 clicks; save Project 8 for after you've actually built at least two of the others — it assumes fluency across nearly the whole handbook.
