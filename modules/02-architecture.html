Kafka Architecture

Module 1 called Kafka "a distributed, append-only log." This module opens that phrase up piece by piece: what a broker actually is, how a topic gets split and copied across a cluster, and how the cluster keeps agreeing on the truth even when machines die mid-write.

2.1 The cluster at a glance

A Kafka deployment is called a cluster — a set of server processes called brokers working together. Producers write to the cluster; consumers read from it; the cluster itself handles replication, failover, and ordering guarantees underneath.

2.2 Brokers

A broker is a single Kafka server process. It accepts writes from producers, serves reads to consumers, and stores partition data on its local disk. Each broker has a unique numeric ID. A production cluster typically runs 3, 5, or more brokers — never one, since that would remove the durability Kafka is built for.

Brokers are largely stateless about which data they hold in the sense that partition assignment can move between brokers (during rebalancing or when a broker joins/leaves) — but at any moment, each broker knows exactly which partitions it currently leads or replicates, and that assignment is tracked centrally (via KRaft's controller quorum, covered in 2.9).

2.3 Topics & Partitions

A topic is a named stream of events — order-events, payment-events, click-stream. It's a logical category, not a physical file. Under the hood, every topic is split into one or more partitions, and it's the partition — not the topic — that is the actual physical, ordered, append-only log.

Why split a topic into partitions at all? Two reasons:

  • Parallelism — a topic with 12 partitions can be read by up to 12 consumers in the same group simultaneously, each handling a slice independently.
  • Scalability — partitions can live on different brokers, so a single topic's total throughput isn't capped by one machine's disk or network.
Trade-off — ordering is only guaranteed within a partition, never across partitions of the same topic. If two events must be strictly ordered relative to each other, they must be written to the same partition — which is exactly what a message key is for (Module 5).

2.4 Offsets

An offset is simply the position of a record within its partition — a monotonically increasing integer starting at 0. Offsets are per-partition, not per-topic and not global. Offset 5 in Partition 0 and offset 5 in Partition 1 are two completely unrelated records.

Critically, the broker does not track what a consumer has read — the consumer does, by committing the offset it has processed up to. This is the "dumb broker, smart consumer" design from Module 1, and it's what lets Kafka support replay: a consumer can simply reset its committed offset backward and re-read history.

2.5 Producers & Consumers (preview)

Two client roles interact with the cluster — full detail lives in their own modules, but the shape here:

  • Producers (Module 5) write records to a topic. A producer decides, via a partitioner, which partition each record lands in.
  • Consumers (Module 6) read records from one or more partitions, tracking their own offset, usually organized into consumer groups for parallel, coordinated reading.

2.6 Consumer Groups

A consumer group is a named set of consumer instances that split up a topic's partitions between them so each partition is read by exactly one consumer in that group at a time. This is what gives you horizontal read scaling: 6 partitions with 3 consumers in a group means each consumer handles 2 partitions. Add a 4th consumer and Kafka rebalances so work is spread across 4 instead.

Rule to memorize — a partition can be read by only one consumer within a given group at any moment, but the same partition can be read simultaneously by consumers in a different group. This is exactly the queue-vs-pubsub duality from Module 1.8.

2.7 Replication: Leaders & Followers

Every partition is replicated across multiple brokers for fault tolerance, controlled by the topic's replication factor (commonly 3 in production). Among the replicas of a given partition, exactly one broker is elected the leader; the rest are followers.

  • All reads and writes for that partition go through the leader — clients never talk to followers directly for a partition they don't lead.
  • Followers continuously fetch and replicate the leader's log, staying ready to take over instantly if the leader fails.
  • If the leader broker crashes, one of the in-sync followers is promoted to leader automatically — this is what makes Kafka tolerate broker failure without data loss or downtime for that partition.

2.8 In-Sync Replicas (ISR)

The ISR (In-Sync Replica set) is the list of replicas — leader plus followers — that are fully caught up with the leader's log within a configurable time bound (replica.lag.time.max.ms). Only replicas in the ISR are eligible for leader election.

A follower that falls behind (slow disk, network partition, GC pause) is dropped from the ISR. It keeps trying to catch up in the background, but until it does, it cannot be promoted to leader — this is exactly what prevents a lagging replica from being elected leader and silently losing acknowledged data.

2.9 ZooKeeper vs KRaft

Someone has to track cluster metadata: which brokers exist, which partition each broker leads, and who's allowed to become leader next. For most of Kafka's life, that job belonged to Apache ZooKeeper, a separate distributed coordination system Kafka depended on.

For this handbook — every install and config example from Module 3 onward assumes KRaft mode, since that's what any new cluster you build today will use.

2.10 Putting it all together

2.11 Common mistakes

  • Assuming more partitions is always better — more partitions means more open file handles, more replication traffic, and slower leader elections; it's a real trade-off, detailed in Module 14.
  • Setting replication factor to 1 in production "to save resources" — this means any single broker failure loses that partition's data entirely.
  • Confusing "in-sync" with "alive" — a follower can be alive and connected but still out of the ISR if it's lagging.
  • Expecting ZooKeeper documentation/tutorials to apply to a new cluster — as of Kafka 4.0, new clusters use KRaft only.

2.12 Check your understanding

Q1. If a topic has 6 partitions and a consumer group has 8 consumer instances, what happens to the 2 extra consumers?
They sit idle. A partition can only be read by one consumer per group at a time, so with 6 partitions the maximum useful parallelism in one group is 6 consumers — the other 2 get no partitions assigned.
Q2. A follower replica is alive and connected, but hasn't replicated the last 10 seconds of writes due to a disk slowdown. Can it become the new leader if the current leader crashes right now?
No — if it has fallen behind past replica.lag.time.max.ms, it has been removed from the ISR, and only ISR members are eligible for leader election. Promoting it would silently lose acknowledged data.
Q3. What single component did KRaft mode remove from a Kafka deployment, and what did it replace it with?
It removed the external Apache ZooKeeper ensemble and replaced it with a built-in Raft-based controller quorum running on the brokers themselves.

2.13 Summary

A Kafka cluster is a set of brokers; each topic is split into partitions, which are the real unit of storage, parallelism, and ordering. Every partition has one leader and zero or more in-sync followers, and only ISR members can be promoted on failure. Consumer groups divide up partitions for parallel, coordinated reading. KRaft mode has replaced ZooKeeper as the system that keeps all of this metadata consistent across the cluster.
