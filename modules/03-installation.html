Installation

Every install path below sets up KRaft mode (Module 2.9) — no ZooKeeper. Pick the path that matches how you'll actually run Kafka day to day.

3.1 Prerequisites

  • Java 17 or newer (Kafka runs on the JVM regardless of which client language you use).
  • At least 2 vCPU / 4 GB RAM for a single-node dev cluster; production brokers typically get dedicated fast disks (SSD/NVMe), since Kafka is disk-throughput bound.

3.2 Linux / macOS — quickstart binary

# download and extract (check kafka.apache.org for the current version)
tar -xzf kafka_2.13-3.9.0.tgz
cd kafka_2.13-3.9.0

# generate a cluster ID and format storage for KRaft mode
KAFKA_CLUSTER_ID="$(bin/kafka-storage.sh random-uuid)"
bin/kafka-storage.sh format --standalone -t $KAFKA_CLUSTER_ID -c config/server.properties

# start the broker (acts as broker + controller in dev mode)
bin/kafka-server-start.sh config/server.properties

That's a fully functional single-node KRaft cluster. Verify it's alive:

bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
# (empty output — no topics yet, but no connection error either)

3.3 Windows

Kafka ships .bat equivalents of every script under bin\windows\. Same steps as Linux, substituting the script extension:

bin\windows\kafka-storage.bat format -t %KAFKA_CLUSTER_ID% -c config\kraft\server.properties
bin\windows\kafka-server-start.bat config\kraft\server.properties
Reality check — most teams developing on Windows just run Kafka inside Docker or WSL2 rather than the native Windows scripts, since the JVM + filesystem behavior on native Windows has more rough edges under load.

3.4 Docker (single broker, fastest path)

docker run -d --name kafka -p 9092:9092 \
  -e KAFKA_NODE_ID=1 \
  -e KAFKA_PROCESS_ROLES=broker,controller \
  -e KAFKA_LISTENERS=PLAINTEXT://:9092,CONTROLLER://:9093 \
  -e KAFKA_ADVERTISED_LISTENERS=PLAINTEXT://localhost:9092 \
  -e KAFKA_CONTROLLER_QUORUM_VOTERS=1@kafka:9093 \
  -e KAFKA_CONTROLLER_LISTENER_NAMES=CONTROLLER \
  apache/kafka:3.9.0

For a real multi-broker dev cluster with Docker Compose, see the full setup in Module 15.

3.5 Kubernetes

Running raw Kafka manifests on Kubernetes by hand is not recommended — StatefulSets, persistent volumes, and broker identity all need careful coordination. Use the Strimzi operator, covered end-to-end in Module 16.

3.6 Cloud installation

  • Confluent Cloud — fully managed Kafka-as-a-service, no broker management at all.
  • Amazon MSK — managed Kafka on AWS, covered fully in Module 17.
  • Self-managed on EC2/GCE/Azure VMs — same binary install as 3.2, with attention to EBS/persistent-disk throughput and cross-AZ placement for real fault tolerance.

3.7 Verifying your install

# create a test topic
bin/kafka-topics.sh --create --topic test-topic --bootstrap-server localhost:9092 \
  --partitions 3 --replication-factor 1

# produce a message
echo "hello kafka" | bin/kafka-console-producer.sh --topic test-topic --bootstrap-server localhost:9092

# consume it back
bin/kafka-console-consumer.sh --topic test-topic --from-beginning --bootstrap-server localhost:9092
# => hello kafka

3.8 Common mistakes

  • Using replication-factor 1 beyond a local dev test — fine here, dangerous in anything shared.
  • Forgetting to set KAFKA_ADVERTISED_LISTENERS correctly in Docker — clients outside the container get an unreachable internal hostname back and connections silently fail after the initial handshake.
  • Mixing an old ZooKeeper-mode server.properties template with a new KRaft install — the property sets are different; use the KRaft template that ships with your version.

3.9 Summary

Every environment — bare metal, Docker, Kubernetes, or cloud-managed — converges on the same KRaft-mode broker underneath. Get comfortable with the raw binary install first; Docker (Module 15) and Kubernetes (Module 16) are just packaging around the same kafka-server-start process.
