Security

Every quickstart in Module 3 ran with zero security — fine for a laptop, unacceptable for anything with real data flowing through it. Three independent layers make Kafka production-safe: encryption in transit, authentication, and authorization.

12.1 SSL/TLS — encryption in transit

SSL encrypts traffic between clients and brokers (and between brokers themselves) so data isn't readable on the wire. Configured per-listener:

# server.properties
listeners=SSL://:9093
ssl.keystore.location=/var/kafka/ssl/kafka.keystore.jks
ssl.keystore.password=changeit
ssl.truststore.location=/var/kafka/ssl/kafka.truststore.jks
ssl.truststore.password=changeit

12.2 SASL — authentication

SASL (Simple Authentication and Security Layer) verifies who is connecting. Kafka supports several mechanisms:

MechanismHow it works
SASL/PLAINUsername + password, typically layered under SSL so credentials aren't sent in the clear
SASL/SCRAMSalted challenge-response — credentials stored as a hash, not plaintext, inside Kafka itself
SASL/GSSAPI (Kerberos)Enterprise SSO integration, common in large regulated environments
SASL/OAUTHBEAREROAuth2 token-based auth, common with cloud-managed Kafka and modern identity providers
# client config for SASL/SCRAM over SSL
security.protocol=SASL_SSL
sasl.mechanism=SCRAM-SHA-256
sasl.jaas.config=org.apache.kafka.common.security.scram.ScramLoginModule required \
  username="app-producer" password="secret";

12.3 ACLs — authorization

Authentication answers "who are you?" — ACLs (Access Control Lists) answer "what are you allowed to do?" Kafka's authorizer checks every request against configured ACLs before allowing it.

# allow app-producer to write to the orders topic only
bin/kafka-acls.sh --bootstrap-server localhost:9092 \
  --add --allow-principal User:app-producer \
  --operation Write --topic orders

# allow fraud-detector group to read orders
bin/kafka-acls.sh --bootstrap-server localhost:9092 \
  --add --allow-principal User:fraud-detector \
  --operation Read --topic orders --group fraud-detector

12.4 Encryption at rest

Kafka itself doesn't encrypt data on disk natively — encryption at rest is typically handled at the infrastructure layer: encrypted EBS volumes on AWS, encrypted persistent disks on GCP, or disk-level encryption (LUKS) for self-managed deployments.

12.5 Putting the layers together

12.6 Common mistakes

  • Running SASL without SSL — credentials for SASL/PLAIN travel in the clear without transport encryption underneath.
  • Granting broad ACLs ("allow all") "to unblock a deploy" and never tightening them afterward.
  • Forgetting inter-broker traffic also needs securing — a cluster with client-facing SSL but plaintext broker-to-broker replication still leaks data.

12.7 Summary

Kafka security is three independent, stackable layers: SSL for encryption in transit, SASL for authentication, and ACLs for fine-grained authorization — plus infrastructure-level encryption at rest. Skipping any one layer leaves a real, specific gap, not just theoretical risk.
