Best Practices

The last segment in the log. Everything here is a decision worth making deliberately, up front — not a default worth leaving unexamined.

23.1 Topic naming

  • Use a consistent, hierarchical convention: <domain>.<entity>.<event-type> — e.g. orders.order.placed, payments.transaction.completed.
  • Avoid environment names inside the topic name (orders-prod) — separate environments should mean separate clusters, not separate naming schemes on one cluster.
  • Pick past-tense event names (OrderPlaced, not PlaceOrder) — a topic carries facts about what happened, not commands (Module 1.7).

23.2 Partition sizing

  • Size for your target consumer parallelism and realistic per-partition throughput, not just current traffic — remember partition count can only increase, never decrease (Module 7.4).
  • A reasonable starting range for moderate-traffic topics is 6–12 partitions; extremely high-throughput topics may need dozens, but each additional partition has a real cost (open file handles, replication traffic, slower elections).
  • Revisit based on actual lag metrics (Module 6.5), not speculative future load.

23.3 Replication factor

  • Production default: replication factor 3, min.insync.replicas=2 — tolerates one broker failure with zero data loss for acks=all producers.
  • Never run replication factor 1 outside of local development — a single broker failure loses that partition's data entirely.
  • Spread replicas across independent failure domains (AZs/racks) — replication factor only protects you if replicas can't all fail together (Module 17.1).

23.4 Security

  • All three layers, always in production: SSL for encryption, SASL for authentication, ACLs for authorization (Module 12) — not just the ones that felt urgent at launch.
  • Scope ACLs to least privilege per service/team — "allow all to unblock a deploy" is the kind of shortcut that outlives its justification.
  • Encrypt inter-broker traffic, not just client-facing traffic — replication data is real data too.

23.5 Monitoring

  • Alert on the shortlist from Module 13.2: UnderReplicatedPartitions, ActiveControllerCount, consumer lag trend, request latency percentiles, disk usage trend.
  • Alert on lag trend, not absolute lag — a stable large number can be healthy; a small but rapidly growing number is the real warning.
  • Treat disk usage as a hard-alert metric, not a dashboard — Kafka's failure mode here (stop accepting writes) doesn't degrade gracefully.

23.6 Scaling

  • Scale consumers up to (but not past) partition count — extra instances beyond that sit idle (Module 2.11).
  • Prefer cooperative rebalancing (CooperativeStickyAssignor) in any cluster where consumer group membership changes often.
  • Treat partition reassignment as a deliberate, monitored operation (via kafka-reassign-partitions.sh), not something to run casually on a live production topic.

23.7 Schema & data contracts

  • Every multi-team topic should go through Schema Registry with an explicit compatibility mode (Module 11.4) — "we'll coordinate in Slack" is not a contract.
  • Default to BACKWARD compatibility unless you have a specific reason for something looser.
  • Use the outbox pattern (Module 19.4) for any service that needs to keep its own database and its Kafka events consistent.

23.8 The one-page mental model

If you remember nothing else from this handbook — Kafka is a distributed, append-only log. Partitions are the real unit of ordering and parallelism. Producers decide durability via acks; consumers decide correctness via when they commit offsets. Everything else in this handbook — Streams, Connect, Schema Registry, security, Kubernetes, MSK — is infrastructure built around that one core idea.

23.9 Where to go from here
