Kafka Storage Internals

A partition isn't one giant file — it's a directory of smaller files called segments. That single design decision is why retention, compaction, and deletion can all happen without ever rewriting the active log.

8.1 Log segments

Each partition's log is split into segments — files typically capped by size (log.segment.bytes, default 1 GB) or age (log.roll.ms). Only the newest segment, the active segment, accepts new writes; older segments are immutable and read-only.

Each .log segment is paired with a .index file (offset → byte position) and a .timeindex file (timestamp → offset), which is how a consumer requesting "give me everything after 3pm yesterday" resolves quickly without scanning the whole log.

8.2 Retention

Retention decides when old segments are deleted, controlled per-topic:

  • retention.ms — delete segments older than this (default 7 days).
  • retention.bytes — cap total partition size, deleting oldest segments once exceeded.

Because deletion happens at the segment level, not per-record, Kafka never has to rewrite a file to remove old data — it just deletes whole closed segment files once every record in them is past the retention window.

8.3 Compaction

Time-based retention deletes old data outright. Log compaction (cleanup.policy=compact) takes a different approach: for each key, it keeps only the latest value, forever, discarding older values for that same key. This turns a topic into something like a durable key-value snapshot, replayable from scratch.

A special value — a tombstone (a record with the key but a null value) — marks a key for deletion; compaction removes it entirely after a configurable delay, giving consumers time to see the delete before it disappears.

8.4 Cleanup policies

PolicyBehaviorUse case
delete (default)Removes whole segments past retention time/sizeEvent streams, logs — history has a natural expiry
compactKeeps only the latest value per key, foreverChangelog topics, "latest state per entity" topics
compact,deleteBoth — compact by key, and also expire very old recordsLatest-state topics that also need a hard data-age ceiling (e.g. compliance)

8.5 Disk layout

    ...
  orders-1/

Each partition is its own directory named <topic>-<partition>. Because Kafka relies heavily on sequential disk writes (append-only) and the OS page cache for reads, it's disk-throughput bound rather than IOPS-bound — fast sequential-write SSDs matter more than raw random IOPS.

8.6 Common mistakes

  • Using compact cleanup policy on a topic that isn't naturally keyed (e.g. logs with no meaningful key) — you'll silently lose data you actually needed.
  • Setting retention far shorter than downstream consumers' realistic recovery/reprocessing window — a consumer down for a long weekend can lose data it needed to replay.
  • Ignoring disk throughput in capacity planning and only sizing for disk space — Kafka's bottleneck is almost always sequential write/read bandwidth.

8.7 Check your understanding

Q1. Why can Kafka delete old data without rewriting any files?
Because a partition's log is split into immutable segment files. Retention just deletes whole closed segment files once every record inside is past the retention window — no in-place rewriting needed.
Q2. What does log compaction guarantee that time-based retention doesn't?
Compaction guarantees the latest value for every key is retained forever, regardless of age — useful for "current state" topics — whereas time-based retention deletes everything past an age threshold, keys included.

8.8 Summary

Partitions are physically stored as a sequence of immutable segment files, which is what makes both retention (delete whole old segments) and compaction (keep only the latest value per key) cheap operations rather than expensive rewrites. Choosing the right cleanup policy per topic is a core design decision, not an afterthought.
