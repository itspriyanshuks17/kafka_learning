Consumers

The producer's job ends the moment a record is durably written. Everything about correctness after that — did we process this exactly once, what happens when a consumer dies mid-batch — is the consumer's problem. This module is about owning that problem deliberately.

6.1 The Consumer API — Java

Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("group.id", "fraud-detector");
props.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
props.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
props.put("enable.auto.commit", "false");

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(List.of("orders"));

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String, String> r : records) {
        process(r.key(), r.value());
    }
    consumer.commitSync(); // commit only after processing succeeds
}

6.2 Consumer groups, revisited

Every consumer belongs to a consumer group (group.id). Kafka's group coordinator assigns each partition of the subscribed topic(s) to exactly one consumer instance within that group. This is the mechanism from Module 2.6 — the actual assignment protocol is what makes both scaling out and automatic failover work.

6.3 Offset management: auto vs manual commit

Auto commitManual commit
Configenable.auto.commit=true (default), commits every auto.commit.interval.msenable.auto.commit=false, call commitSync()/commitAsync() explicitly
RiskOffset can commit before processing finishes — a crash mid-batch silently skips unprocessed recordsYou control exactly when "processed" means "safe to commit"
Best forSimple, loss-tolerant pipelines (metrics, logs)Anything where losing or double-processing a record has real cost
// commit synchronously, after processing, blocking until the broker acks
consumer.commitSync();

// commit asynchronously — faster, but failures are only reported via callback
consumer.commitAsync((offsets, exception) -> {
    if (exception != null) log.error("commit failed", exception);
});

6.4 Rebalancing

A rebalance is the group coordinator reassigning partitions among consumers — triggered when a consumer joins, leaves, crashes, or is considered dead (missed heartbeats past session.timeout.ms). During a classic "stop-the-world" rebalance, all consumers in the group pause processing until reassignment completes.

Modern Kafka supports cooperative rebalancing (CooperativeStickyAssignor), which reassigns only the partitions that actually need to move, instead of revoking everything from everyone first — dramatically shortening the pause.

6.5 Consumer lag

Lag is the gap between the latest offset written to a partition (log-end-offset) and the offset a consumer group has committed. It's the single most important health metric for a Kafka consumer — rising lag means the consumer can't keep up with the producer's write rate.

bin/kafka-consumer-groups.sh --describe --group fraud-detector --bootstrap-server localhost:9092
# LAG column climbing steadily = consumer is falling behind, needs more instances or faster processing

6.6 Common mistakes

  • Leaving auto-commit on for a pipeline where losing a record on crash is unacceptable.
  • Processing records slowly enough that poll() isn't called within max.poll.interval.ms — the consumer is then considered dead and the group rebalances even though the process is still alive, just busy.
  • Scaling consumers past the partition count — extra instances sit idle (Module 2.11), so partition count is a real ceiling on consumer-side parallelism.
  • Committing offsets before processing completes, turning "at-least-once" into an accidental "at-most-once."

6.7 Check your understanding

Q1. A consumer commits its offset right after calling poll(), before processing the batch. What delivery guarantee does this actually give you, despite intending at-least-once?
At-most-once — if the process crashes after the commit but before finishing processing, those records are skipped forever since the committed offset says they were handled.
Q2. Consumer lag is climbing steadily even though CPU usage on the consumer looks fine. What are two likely causes?
Either the consumer count is below the partition count so throughput is capped, or per-record processing (e.g. a slow downstream call) is the bottleneck rather than CPU — profiling the processing loop, not the CPU graph, is the next step.

6.8 Summary

Consumer groups give you parallel, coordinated reading; manual offset commits give you control over exactly what "processed" means; cooperative rebalancing minimizes the pause when group membership changes; and lag is the metric that tells you, in real time, whether your consumers are actually keeping up.
