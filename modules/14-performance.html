Performance Tuning

Kafka's defaults are tuned for balance, not your specific workload. Tuning is always a trade: throughput vs latency, durability vs speed. Know which side of each trade your system actually needs before touching a config.

14.1 Producer tuning

SettingEffect
batch.sizeLarger batches = fewer requests, better throughput, slightly higher latency per record
linger.msDeliberately waits this long to fill a batch before sending — trades a few ms of latency for much better throughput under load
compression.typelz4 or zstd shrink network/disk usage significantly with low CPU cost; almost always worth enabling
buffer.memoryTotal memory the producer can use to buffer unsent records — too small causes send() to block under bursty load
props.put("batch.size", "32768");
props.put("linger.ms", "10");
props.put("compression.type", "lz4");
props.put("buffer.memory", "67108864");

14.2 Consumer tuning

SettingEffect
fetch.min.bytesBroker waits until this much data is available before responding — larger values improve throughput, add latency
max.poll.recordsCaps records per poll — tune down if per-record processing is slow, to avoid missing the poll interval and triggering a rebalance
fetch.max.wait.msMaximum time broker waits before responding even if fetch.min.bytes isn't met — bounds worst-case latency

14.3 Broker tuning

  • Partition count per broker — too many partitions per broker increases metadata overhead and can slow controller failover; there's a practical ceiling, not "more is always fine."
  • Page cache — Kafka relies heavily on the OS page cache for reads; leave headroom rather than sizing the JVM heap too large and starving the cache.
  • num.io.threads / num.network.threads — tune upward on brokers handling high concurrent request volume.

14.5 Common mistakes

  • Enabling compression only on the producer side and forgetting brokers/consumers handle it transparently — this one's actually automatic, but teams sometimes re-compress downstream unnecessarily.
  • Chasing lower latency with linger.ms=0 on a high-volume pipeline where throughput actually matters more, leaving real capacity on the table.
  • Sizing JVM heap too large "for safety" and starving the OS page cache Kafka depends on for fast reads.

14.6 Summary

Producer tuning is mostly about batching and compression; consumer tuning is about balancing poll size against processing speed; broker tuning is about not starving the OS page cache. Every setting here trades latency against throughput — tune toward whichever your actual SLA demands, not toward "faster" in the abstract.
