Producers

A producer's job sounds simple — send a record — but every default it ships with is a deliberate trade-off between speed, durability, and ordering. This module is about knowing which knob to turn for which guarantee.

5.1 The Producer API — Java

import org.apache.kafka.clients.producer.*;
import java.util.Properties;

Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
props.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
props.put("acks", "all");

KafkaProducer<String, String> producer = new KafkaProducer<>(props);

ProducerRecord<String, String> record =
    new ProducerRecord<>("orders", "order-101", "{\"status\":\"placed\"}");

producer.send(record, (metadata, exception) -> {
    if (exception != null) {
        // handle failure — retry logic, dead-letter, alerting
    } else {
        System.out.printf("sent to partition %d at offset %d%n",
            metadata.partition(), metadata.offset());
    }
});
producer.close();

5.2 The Producer API — Python (confluent-kafka)

from confluent_kafka import Producer

conf = {'bootstrap.servers': 'localhost:9092', 'acks': 'all'}
producer = Producer(conf)

def delivery_report(err, msg):
    if err is not None:
        print(f'delivery failed: {err}')
    else:
        print(f'delivered to {msg.topic()} [{msg.partition()}] @ {msg.offset()}')

producer.produce('orders', key='order-101', value='{"status":"placed"}', callback=delivery_report)
producer.flush()

5.3 Serialization

Kafka stores everything as raw bytes — it has no idea what a "string" or "JSON object" is. Serializers convert your language's objects into bytes on the way in; deserializers do the reverse on the way out. Common choices: StringSerializer (JSON-as-text), ByteArraySerializer (pre-serialized bytes), and Avro/Protobuf serializers backed by Schema Registry (Module 11) for strict, versioned contracts.

5.4 Keys & partitioning

The key you attach to a record determines which partition it lands in — by default, Kafka hashes the key (murmur2(key) % numPartitions) so the same key always routes to the same partition, which is exactly how you get ordering guarantees for a given entity (e.g. all events for order-101 land in the same partition, so they're processed in order).

  • No key (null) — records are spread round-robin (or "sticky batch" in newer clients) across partitions for maximum load balancing, but with zero ordering guarantee between records.
  • Custom partitioner — you can implement your own logic (e.g. route VIP customers to a dedicated partition) by supplying a Partitioner implementation.
Common bug — changing a topic's partition count changes the hash-to-partition mapping for all future messages. Existing keys can suddenly route to a different partition, breaking the ordering assumption your consumers relied on. Plan partition counts up front (Module 14).

5.5 Acknowledgements (acks)

acksMeaningTrade-off
0Producer doesn't wait for any acknowledgementFastest, but messages can be silently lost
1Waits for the partition leader to write the recordSafe from most failures, but data can be lost if the leader crashes before followers replicate it
all / -1Waits for all in-sync replicas (ISR, Module 2.8) to acknowledgeStrongest durability guarantee; combine with min.insync.replicas to fail fast if too few replicas are in sync

5.6 Delivery guarantees

  • At-most-once — acks=0 or no retries; a message might be lost, never duplicated.
  • At-least-once — retries enabled with acks=all; a message is never lost, but network hiccups can cause duplicate sends.
  • Exactly-once — enabled via the idempotent producer plus transactions (5.7–5.8); no loss, no duplication, even across retries and consumer restarts.

5.7 Idempotent producer

Setting enable.idempotence=true assigns each producer a unique ID and each message a sequence number; the broker deduplicates any retry that would otherwise create a duplicate. This turns "at-least-once with retries" into "exactly-once, per partition, per producer session" — with effectively no throughput cost, which is why it's the default in modern Kafka clients.

props.put("enable.idempotence", "true");
// acks is forced to "all" automatically when idempotence is enabled

5.8 Transactions

Idempotence guarantees exactly-once for a single partition. Transactions extend that guarantee across multiple partitions and topics — critical for "read from topic A, process, write to topic B" pipelines (exactly how Kafka Streams gets its exactly-once guarantee).

props.put("transactional.id", "order-processor-1");
KafkaProducer<String, String> producer = new KafkaProducer<>(props);
producer.initTransactions();

try {
    producer.beginTransaction();
    producer.send(new ProducerRecord<>("orders-validated", key, value));
    producer.send(new ProducerRecord<>("audit-log", key, auditValue));
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();
}

5.9 Common mistakes

  • Using acks=1 for financial or otherwise loss-sensitive data — the small durability gap vs acks=all is exactly where lost records hide.
  • Sending without a key when order matters — round-robin partitioning has no ordering guarantee across partitions.
  • Ignoring the delivery callback / future — silent failures are the most common way "missing data" bugs get reported weeks later.
  • Setting batch size and linger.ms to defaults for a high-throughput pipeline and leaving real throughput on the table (tuned properly in Module 14).

5.10 Check your understanding

Q1. Why does sending records with the same key guarantee they're processed in order, while null-key records don't?
Keys are hashed to deterministically select a partition, and ordering is only ever guaranteed within a single partition. Null-key records are spread across partitions for load balancing, so there's no single ordered log they all share.
Q2. What's the practical difference between the idempotent producer and using transactions?
Idempotence prevents duplicate writes within a single partition from producer retries. Transactions extend that atomicity across multiple partitions/topics, so a multi-topic write either all commits or all rolls back together.

5.11 Summary

Producers trade off speed against durability through acks, get ordering through key-based partitioning, and reach exactly-once semantics through idempotence plus transactions. Almost every production incident involving "missing" Kafka data traces back to one of these settings being left at a default that doesn't match the data's actual durability requirements.
